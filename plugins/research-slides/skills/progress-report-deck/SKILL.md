# 進捗報告スライド作成スキル

研究室の進捗報告スライドを、**既存の pptx をコピーして中身を差し替える**方式で作る。ゼロから作るより、デザインを確実に揃えられるため。どのフォルダで作業していても使え、新しい pptx はカレントディレクトリに作る。

このスキルのスクリプトとテンプレートは **`${CLAUDE_SKILL_DIR}`** にある（`scripts/` と `assets/`）。作業フォルダとは別の場所なので、呼び出すときは必ず `${CLAUDE_SKILL_DIR}/...` の絶対パスで指定する（相対パスでは届かない）。

## プロフィール（利用者ごとの情報）

氏名・所属・ファイル名の規則などの利用者ごとの情報は、スキルの外にある **プロフィールファイル** `~/.claude/yapi-skills/profile.md`（Windows なら `%USERPROFILE%\.claude\yapi-skills\profile.md`）に置く。スキルを更新しても消えないようにするため。

- 作業の最初に読む。`## 共通` と `## research-slides` の節を使う
- **無ければ**、`AskUserQuestion` で氏名・所属・研究室・学年・研究分野を聞き、「プロフィールに保存してよいか」を確認してから、`${CLAUDE_SKILL_DIR}/references/profile-template.md` の形で書く。保存を断られたら、その回だけ使う
- プロフィールの「独自ルール」（配色・最小の文字サイズ・ファイル名など）は、このファイルの既定のルールより優先する

## ベースにする資料

- カレントディレクトリ（またはユーザーが指定した場所）に `*進捗報告*.pptx`（プロフィールにファイル名の規則があればそれに合うもの）があれば、その中で一番新しいもの
- 無ければ、同梱の `${CLAUDE_SKILL_DIR}/assets/template.pptx`
- どちらにするか迷ったらユーザーに確認する

**月次の資料を前回から作るときの作法**:
- 土台は前回の**最終版**（実際に発表したもの）。`_v2` `_修正前` `下書き` のような途中の版が並んでいたら、どれが最終版かユーザーに確認する
- 引き継ぐのは**体裁**（レイアウト・配色・骨格・据え置きの研究背景）だけ。目次・今回の小目標・数値・主張は前回から写さず、**今回の記録から取り直す**（前回の数値が残っていても「たぶん同じ」で済ませない）
- 前回の資料でユーザーが消した要素・直した言い回しは、そのまま正とする（勝手に元に戻さない、同梱テンプレートの型で上書きしない）

利用者自身の過去資料をベースにする場合、スライドレイアウトの番号やテーマの色は同梱テンプレートと違うことがある。最初に `ppt/slideLayouts/` とテーマの色を確認し、下のデザインルールのうち色に関するものは、その資料のテーマの accent1 / accent2 に読み替える（`deck_style.palette_from_theme()` で読める）。

**同梱テンプレート `assets/template.pptx`**（4:3・全18枚・匿名化したサンプル）。論文の査読対応の回を題材にした見本で、**下記のデザインルールをすべて適用済み**。文字はダミーで、どの型にどんな文を入れるかの見本を兼ねる。

| 枚 | 内容 | 流用できる型 |
|---|---|---|
| 1 | タイトル | そのまま（月・所属・氏名を差し替え） |
| 2 | 今月行ったこと | 目次の箇条書き（縦中央寄せ） |
| 3 | 研究背景(1/2) | 図＋注釈（枠線の円）、引用文献の16pt表記 |
| 4 | 研究背景(2/2) | 図＋色分けした注釈ラベル・吹き出し |
| 5 | 研究目的 | チップ＋パネル（「目的」「今回の小目標」）＝**配色の基準** |
| 6 | 全体サマリ | 上帯＋2カラム比較＋下帯（濃紺） |
| 7, 11 | 指摘への対応 | **チップ＋パネル（指摘＝橙／対応＝青）** |
| 8-9 | 個別コメント対応(1/2)(2/2) | 番号バッジ＋パネル |
| 10 | 最重要指摘 | 圧縮した本文＋**Before/After 模式図**（角丸四角＋矢印） |
| 12 | 評価方法の明確化 | 本文＋**タイムライン模式図**（実線／破線ボックス＋コネクタ） |
| 13 | 比較手法の設定 | 2カラムのチップ＋パネル＋下帯、**OMML数式** |
| 14 | 主要な結果 | **表**（濃紺ヘッダ・主役行を淡青で強調）＋全幅の帯3本 |
| 15 | 追加検証 | **KPIタイル2×2** |
| 16 | ページ数超過への対応 | Before/After ＋ **チェックリスト** |
| 17 | まとめ・課題 | 枠線ボックス2段（まとめ／今後の展望） |
| 18 | ご清聴ありがとうございました | そのまま |

数式定義の見本は `assets/eqdefs-example.js`（学習窓・探索半径・位置予測・状態ベクトル・カルマンフィルタの Q/R/P₀）。

## 必要な環境

最初に `python --version` / `node --version` / `pip list` で確認する。

- **Python 3.10+**（Windows で `python` が通らなければ `py`）。`python-pptx` `Pillow` `defusedxml` `lxml` `markitdown[pptx]` `pymupdf` が必要。無ければ `pip install python-pptx Pillow defusedxml lxml "markitdown[pptx]" pymupdf`
- **Node.js**（`check-min-font.js` などのスクリプト用）
- **PowerPoint 本体**（Windows のみ・任意）— COM 経由で PDF 化して **本番と同じ見え方** を確認できる（`render_with_powerpoint.py`）。あれば最終確認はこちらで行う
- **LibreOffice**（`soffice`）— 速い簡易確認用（`render_slides.py`）。ただし **OMML 数式は表示できない**（Fallback の平文になる）。PowerPoint が無い環境（Mac・Linux）では LibreOffice で確認し、数式のスライドの最終確認はユーザーに PowerPoint か Keynote で開いてもらう
- `unzip` / `zip`（pptx を ZIP として展開し、XML を直接編集する）

## 同梱スクリプト

すべて `${CLAUDE_SKILL_DIR}/scripts/` にある。

| スクリプト | 用途 |
|---|---|
| `deck_style.py` | 配色パレット＋チップ／パネル／タイル／帯／チェックリスト／主張行（`add_claim`）／結果表（`add_table`）／太字の色戻し（`normalize_bold_color`）／配色の差し替え（`set_palette`・`palette_from_theme`）。python-pptx から import |
| `omml.js` | PowerPoint 正式数式（OMML）の組み立てと `mc:AlternateContent` での埋め込み。`M.hat()`（ハット）・`M.bold()`（ベクトル用太字）もある |
| `insert_math.js` | python-pptx で置いた `@@EQ:名前@@` の仮テキストを OMML 数式に一括置換（数式定義ファイルを渡す） |
| `duplicate-slide.js` | スライド複製（Content_Types・rels・sldIdLst まで面倒を見る） |
| `check_deck.py` | **仕上げの機械チェック**。壊れ（切れた参照・残ったスライドパーツ）、16pt 未満、はみ出し・1〜4字だけ次行に落ちる行（PowerPoint の折り返しを見積もる）、下の空白、パレット外の色、太字の色、仮の文字・テンプレートのダミー文の残り、AI 臭のする語・表記ゆれ。`--text` で構成案の md も検査できる |
| `check-min-font.js` | 16pt 未満の文字だけを検出（展開したフォルダに対して使える軽い版。rebuild.sh の途中などで） |
| `render_with_powerpoint.py` | **PowerPoint 本体**で PDF 化 → PNG（本番同等の確認。Windows のみ） |
| `render_slides.py` | LibreOffice で PDF 化 → JPG（速いが数式は見えない） |

## テンプレートの構成（決まったスライド順）

| # | スライド | 内容 | 毎回変わる？ |
|---|---|---|---|
| 1 | タイトル | 「進捗報告 ◯月」＋大学・学部・学科／研究室・学年／氏名 | 月だけ差し替え |
| 2 | 今月行ったこと | 今回の報告内容を箇条書きで要約（アジェンダ） | 今回の内容に差し替え |
| 3-4 | 研究背景 (1/2)(2/2) | 研究の背景。前回とほぼ同じでよい | 基本据え置き |
| 5 | 研究目的 | 研究の目的＋「今回の小目標」 | 今回の小目標だけ更新 |
| 6〜 | 各トピックの内容スライド | シミュレーション・実験・手法など、今回進めた内容を1トピック1スライドで | 完全に今回の内容 |
| 最後-1 | まとめ・課題 | あれば | 今回の内容 |
| 最後 | ご清聴ありがとうございました | クロージング（中央寄せ、装飾なし） | 変更なし |

内容スライドは1スライド1見出しで、必要に応じて `(1/2)` `(2/4)` のように連番タイトルで分割する（研究背景がその例）。すべての内容スライドの右上にスライド番号（自動フィールド）が入る。

## デザインルール（同梱テンプレートの既定）

レンダリングして目視確認して分かった点を含む。XML だけを見ていると気づけない装飾がレイアウト側に入っているので、**手で再現しようとせず、既存のスライドレイアウト（同梱テンプレートでは slideLayout1=タイトル、slideLayout2=タイトル+本文、slideLayout7=クロージング）を使い続ければ自動的に付いてくる**。

- **スライドサイズ**: 4:3（`cx=9144000 cy=6858000` EMU、10in×7.5in）。ベースの資料のサイズを変えない。
- **フォント**: 日本語は メイリオ で統一。
- **配色はテーマの2色だけ**（最重要。下の「配色パレット」を守る）。
- **タイトルスライド**: 全体を細い枠線で囲んでいる（slideLayout1 由来）。
- **内容スライド共通の装飾**（slideLayout2 由来、触らなくても自動で付く）:
  - タイトル文字がテーマ色、その下に細い下線＋右端に丸ドット
  - 右上にテーマ色で塗った四角バッジの中に白文字でページ番号（自動フィールドなので数字を書く必要なし）
  - これは「タイトル下に装飾線を引くのは AI 生成っぽく見えるので避ける」という一般的な注意とは別物。**この資料の既存の型なので消さない・新しく似せて作らない（レイアウトを使い回せば自動で出る）**
- **図の注釈の付け方**（研究背景スライドが実例）: 塗りなし・色付き枠線の円や四角で対象を囲み、同じ色の枠線を引いた白背景のラベル（角丸なしの四角、テキストボックスに枠線を付けたもの）へ直線でつなぐ。正式な凡例ボックスは作らず、ラベルの文字色・枠色そのもので対応関係を示す。
  - **ここだけは2色ルールの例外**: 写真の上で複数の対象を識別するラベルは、色を変えないと区別できないので要素ごとに色を変えてよい（例: 赤・マゼンタ・オレンジ・グレー）。**写真に載せる識別ラベル以外では、パレットの2色から出ない。**
- **強調は太字だけ。太字の語句に色を付けない**。青・オレンジの太字は淡青／淡橙のパネルの上で背景に紛れて見づらい。太字は標準の文字色（黒 `#1A1A1A`、濃紺の帯の中なら白）のまま。太字にする語句だけ `<a:r>` を分けて `b="1"` を付ける。下線も使ってよい。**1文につき強調は1〜2箇所まで**（全部強調すると読みどころが消える）。
  - 色の意味づけ（青＝提案、オレンジ＝問題・比較手法）は、**チップ・パネルの塗りと枠線**で表す。文字色で表してよいのは、太字でない区分名（表の比較手法名をオレンジにする等）だけ。
  - 保存前に `normalize_bold_color(prs, skip=(据え置くスライドの番号,…))` を呼ぶと、うっかり色を付けた太字も標準色に戻る（チップ・帯の白抜き文字は残る）。
- **分類タグ**: 手法名や区分は色付きの四角バッジ＋白太字で示す（`add_chip()`）。「指摘」「対応」「手法A」などがこれ。
- **文字サイズは全て16pt以上**（最重要ルール。プロフィールで変更されていればそれに従う）。目安:

  | 要素 | サイズ |
  |---|---|
  | タイトルスライドの題目 | 32〜36pt, 太字 |
  | タイトルスライドの所属/氏名 | 18pt（右寄せ） |
  | 各スライドの見出し（タイトルプレースホルダ） | 既定36pt（継承でよい） |
  | 本文の強調見出し（太字ラベル） | 22〜24pt |
  | 本文 | 18〜20pt |
  | 図キャプション・注釈・引用文献 | 16pt（**16pt 未満は絶対に使わない**。過去資料に12ptの引用文献があっても新規作成時は16ptにする） |
  | スライド番号 | 既定18pt（プレースホルダのまま触らない） |

  16pt だと文献情報や図注が入りきらない場合は、文字を小さくするのではなく **箱を広げる／文言を削る／スライドを分ける** で対処する。

## 文章のルール

- **主張の1文（`add_claim`）は結論を書く**。「結果①」「〇〇について」ではなく「速度が上がるほど差が開く」。スライドのタイトルはテンプレートどおり短い見出し（「主要な結果（条件X = 4）」）でよいが、「〜について」「〜を示す」「〜です／ます」で終えない
- **1項目1文**。「。」で2文つながったら箇条を分けるか削る。1文の箇条に「。」は付けない
- **評価語は数値で裏づける**。「大幅に改善」より「誤差が 12% 減った」。「同等」「保証」「有効性を示した」は言い過ぎになりやすい（表で比較手法がわずかに上なら「ほぼ同等」、確かめただけなら「確認した」）
- **未検証のことは未検証と分かる形で書く**（「〜が期待される」「今後検証」）
- 生成した文章にありがちな語（非常に／画期的／〜することが可能／シームレス など）は [references/ai-smell-lexicon.md](references/ai-smell-lexicon.md) を見て普通の言葉に戻す。`check_deck.py` がこのリストで WARN を出す
- 読点は資料の中で「、」か「，」のどちらかに揃える（ベースの資料に合わせる）

## 配色パレット（ここから外れる色を使わない）

同梱テンプレートのテーマは `accent1 = #156082`（青）と `accent2 = #E97132`（オレンジ）の **2色構成**。研究目的スライドがこの2色でできているので、他のスライドも必ずここから選ぶ。**独自の赤（`#C00000` など）は資料全体で浮くので使わない**。

| 用途 | 色 | 由来 |
|---|---|---|
| 見出しチップの背景（対応・提案・結論） | `#104862` | accent1 lumMod75＝研究目的スライドの「目的」バッジと同じ |
| 色付き文字（青）※太字には使わない | `#156082` | accent1 |
| 本文パネルの地色（青系） | `#DBE7F3` | 淡青 |
| 見出しチップの背景（指摘・問題・従来手法） | `#E97132` | accent2＝「今回の小目標」バッジと同じ |
| 色付き文字（オレンジ）※太字には使わない。比較手法名など | `#C55A11` | accent2 lumMod75 |
| 指摘パネルの地色（橙系） | `#FBE3D6` | accent2 lumMod20/lumOff80 |
| 中立パネル・補足 | `#F0F0F0` / 文字 `#595959` | グレー |

**色の意味づけは資料全体で固定する**:
- オレンジ系 = 指摘・問題・従来手法・注意
- 青系 = 対応・提案・結論・主役の数値

定数は `deck_style.py` に定義済み（`NAVY` / `ACCENT1` / `BLUE_LIGHT` / `ORANGE` / `ORANGE_DARK` / `ORANGE_LIGHT` / `GRAY` / `GRAY_LIGHT`）。**テーマの色が違う資料をベースにするとき**は、import の前に配色を差し替える:

```python
import sys; sys.path.insert(0, r"${CLAUDE_SKILL_DIR}/scripts")
import deck_style
deck_style.set_palette(*deck_style.palette_from_theme("ベースの資料.pptx"))   # 派生色も計算し直す
from deck_style import *          # set_palette の「後」に import する
```

## レイアウトの型（スライド下半分を空白のまま残さない）

文字を上に置いただけだと下半分が真っ白になり、「下の余白が大きすぎる」と指摘される。**箇条書きをそのまま流し込まず、下の型のどれかで面を作る**。実装は `deck_style.py` の関数をそのまま呼べばよい。

| 型 | 使いどころ | 関数 |
|---|---|---|
| **チップ＋パネル**（左に「指摘」「対応」などの色付きバッジ、右に本文パネル） | 査読対応・課題と打ち手など「問題→対応」構造。この資料の主役の型 | `add_issue_response()` |
| **番号バッジ＋パネル** | 「1.」「2.」と番号が付く個別項目の列挙 | `add_chip()` + `add_panel()` |
| **KPIタイル（2×2）** | 箇条書き4点程度を面で見せる。数値や結論を大きく | `add_tiles()` |
| **全幅の帯を縦に積む** | 表やグラフの下に「読み取れること」を並べる。1本だけ `NAVY` 塗り＋白文字にすると主役が立つ | `add_bars()` |
| **チェックリスト（✓バッジ）** | 「やったこと／確認したこと」の列挙 | `add_checklist()` |
| **Before/After 模式図** | 手法変更・改善の対比。左=オレンジ枠(従来)、右=青枠(今回)、間に矢印 | 角丸四角＋コネクタで作る（template.pptx の 10枚目が実例） |
| **表＋全幅の帯** | 結果の数値表。主役行（提案手法）を淡青＋太字、比較手法名はオレンジの文字（太字にしない） | `add_table()` + `add_bars()` |
| **図＋右側パネル** | 横長のグラフ画像。図を左に幅 5.2〜5.6M EMU で置き、右の細い列に読み取れることをパネルで縦に積む（1枚目だけ NAVY） | `add_picture()` + `add_panel()` |
| **図2枚縦＋各図の横にチップ＋パネル** | 2つの図をそれぞれ説明する | `add_picture()` + `add_chip()` + `add_panel()` |
| **タイムライン模式図** | 処理の時間的な流れ（前段・本処理・再学習のタイミング・窓）。破線ボックス＝前段、実線の青ボックス＝本処理、▼マーカー、軸、括弧で窓を示す。区間の比率が極端なら「※ 横軸は模式的」と注記して拡大表示する | 四角＋三角形＋コネクタ（template.pptx の 12枚目が実例） |

例外: **「今月行ったこと」（目次）は箇条書きのまま**にする。ここだけは番号バッジ等で飾らず、本文プレースホルダの箇条書き＋キーワードだけ太字（色は付けない）。ただし `<a:bodyPr anchor="ctr">` で縦中央寄せにして、余白が下だけに偏らないようにする。目次の1項目は **全角換算で約20文字**まで（超えると1文字だけ次行に落ちる）。

**主張の1文（構成案に「主張」があるとき）**: タイトル直下に `add_claim(slide, "…")`（y=860,000、20pt 太字・標準色、全幅で約30文字まで）。そのときの本文は `y≈1,450,000` から始める。フロー図などで上部が埋まっているスライドは、代わりに最下部（y≈6,200,000、高さ 480,000）に NAVY の帯で置く。

**縦位置の目安**: 本文は `y=1150000` から始め（主張行があれば `y≈1450000`）、`y=6200000` あたりまでで終える。パネルの高さは中身の行数に合わせ、`anchor=MSO_ANCHOR.MIDDLE` で中身を中央に置く。

**表の列幅の目安（16pt）**: 太字ヘッダの半角10文字程度で約 1.42M EMU、全角7文字で約 1.62M EMU、全角15文字程度の手法名で約 3.3M EMU 必要。足りないとヘッダや手法名が2行に割れて行の高さが伸び、表の下に置いた脚注や帯と重なる。

**折り返しの目安**: 全幅パネル（チップを除いた幅）で 18pt なら日本語 **約30文字**。超えると1〜2文字だけ次行に落ちて不格好になるので、文を削るか `<a:br/>` で明示的に改行する。レンダリング画像で必ず確認する。

## 数式は OMML（PowerPoint の正式な数式）で組む

`r_p(t+1)` のようなプレーンテキストではなく、PowerPoint の数式オブジェクトにする。ヘルパは `scripts/omml.js`。

```js
const { M, wrapShapeWithMath } = require(String.raw`${CLAUDE_SKILL_DIR}/scripts/omml.js`);
// r_p(t+1) = r_p(t) + v_p(t)
const eq = M.oMath(
  M.sSub(M.mr("r"), M.mr("p")) + M.delim(M.mr("t") + M.mrU("+1")) + M.mrU("=") + …
);
xml = wrapShapeWithMath(xml, 8, (useMath) => `<p:txBody>…${useMath ? eq : plainText}…</p:txBody>`, 1850000);
```

実装上の要点（すべて実機で確認済み）:
- `m:r` の書式は `w:rPr` ではなく **`a:rPr`**、フォントは **Cambria Math**。
- `a:rPr` に **文字色を明示する**。省略すると図形既定（`p:style` の `fontRef` が `lt1`＝白）が効いて数式だけ極端に薄くなる。
- `a14:m` を `a:p` 直下にそのまま置くと、**LibreOffice では数式が丸ごと消える**。必ず `p:sp` 全体を `mc:AlternateContent` で包み、`mc:Fallback` にプレーンテキスト版を入れる（`wrapShapeWithMath()` が自動でやる）。
- この形なら pptx スキルの `validate.py` の XSD 検証も PASS する。
- 変数は斜体（`M.mr`）、演算子・数字・`T`（転置）は立体（`M.mrU`）。
- ベクトルの太字は `M.mrU(M.bold("r"))`（数学用太字の文字を立体で置く）、ハットは `M.hat(…)`、`𝒟` のような筆記体は `M.mrU("\u{1D49F}")`。

**python-pptx で作ったパネルに数式を入れる（推奨）**: python-pptx 側で数式を入れたい段落に `("@@EQ:名前@@", False, None)` というランを置いておき（文字サイズはそのランの `sz` が数式に引き継がれる。普通の文字のランと同じ段落に並べてもよい）、保存 → unzip のあとで

```bash
node "${CLAUDE_SKILL_DIR}/scripts/insert_math.js" unpacked eqdefs.js
```

を実行する。`eqdefs.js` は `module.exports = (M) => ({ 名前: [OMMLの中身, Fallbackの平文], … })` の形で書く（`${CLAUDE_SKILL_DIR}/assets/eqdefs-example.js` が実例）。図形ごと `mc:AlternateContent` で包まれ、Fallback には平文が入る。

## 作業の進め方

### 0. プロフィール・作業フォルダ・ベースファイルを決める
- プロフィールを読む（無ければ上の「プロフィール」の手順で作る）。
- 作業フォルダ = ユーザーが今いるカレントディレクトリ（別の場所を指定されたらそこ）。ここに新しい pptx を作る。
- ベースファイル = 上の「ベースにする資料」の順で決める。
- 新しい資料のファイル名はプロフィールの規則（既定は `<氏名>-進捗報告YYYYMM.pptx`）に揃える。YYYYMM はユーザーに確認するか、今回の報告月から決める。

### 1. 今回の報告内容をユーザーから集める
作業フォルダに `スライド作成用.md` のような下書きが置いてあることが多いので、まず読む（`##` 見出しが1スライド相当で書かれていることが多い）。そのうえで `AskUserQuestion` で確認するとよいのは次の3点:

1. **ベースにするファイル**（フォルダ内の既存 pptx か、同梱テンプレートか）
2. **研究目的スライドの「今回の小目標」に書く文言**（実験以外の月＝執筆・査読対応の回は、そのまま書けないので必ず聞く）
3. **図版の扱い**（画像ファイルが無い場合、テキスト＋表だけにするか、模式図をこちらで描き起こすか）

下書きの `##` をそのまま全部スライドにすると枚数が増えすぎることがある。**関連する節は1枚にまとめてよいか**を提案ベースで確認する。

同梱テンプレートから作る場合、研究背景(1/2)(2/2)はダミーなので、**研究背景の中身（何の研究か・図）もユーザーに聞く**（2回目以降は前回の資料をベースにすれば据え置きでよい）。

**構成案ドキュメント形式の下書き**（create-doc スキルの出力。`スライド作成ドキュメント-YYYY-MM-DD.md`＋同じフォルダの `images/`、zip で渡されることもある）:
- 冒頭の「この資料について」は指示（スライドにしない）。発表時間・枚数・表記ルール・配色の割り当て（例: 提案手法＝青、従来版・比較手法＝オレンジ）が書いてあるので最初に読む。
- 各スライドは「型 / 主張 / 本文 / 表・図 / 数式 / ノート」で書かれている。「型」はこのスキルのレイアウトの型の名前と対応する。「主張」はタイトル直下の1文（`add_claim`）。図は `images/<名前>.png` で、新しく作らずそのまま貼る。
- 「想定質問」「出典」の節はスライドにしない。
- **数値は改変・丸め直ししない**。ただし表の値どうしで計算が合わない数値（例: 0.7435 − 0.6572 = 0.0863 なのに「+0.0864」）を見つけたら、直さずにユーザーへ報告する（丸め前の値で計算している可能性がある）。
- **本文の記述が図と合っているかは、図を実際に開いて確かめる**（「〇〇は四隅で大きい」と書いてあっても、図では「右側の隅だけ」ということがある）。

追加で `AskUserQuestion` で確認するとよい点:
- **スピーカーノート**を入れるか（入れない場合、流用したスライドに残っている旧ノートも空にする）。
- **補足（質疑用）スライド**の扱い（クロージングの後ろに「補足A1：…」のようなタイトルで置く）。
- タイトルスライドを「進捗報告 ◯月」のままにするか、発表題目を主題にするか（題目を入れるなら副題として小さく）。
- 「作った方が見やすい模式図は描き起こしてよいか」。

**過去資料の特定の図を使いたいと言われたら**（「前に作った処理フロー図」など）: その pptx を展開して該当の `slideN.xml` を探す。参照しているのが slideLayout だけ（画像なし）なら、複製した枠のスライド XML をそのまま上書きすれば移植できる。描き替えるときは各テキストボックスの段落だけ差し替え、コネクタは接続先を付け替える。

### 2. コピーして展開する
```bash
cp "<ベースファイルのパス>" "<新しいファイル名>.pptx"
mkdir unpacked
cd unpacked && unzip -o -q "../<新しいファイル名>.pptx"
```
ベースが同梱テンプレートの場合、**タイトル・研究背景・研究目的・クロージングは枠として使い回し、6枚目以降の内容スライドは今回の内容に総取り替えする**。その際、上の表の「流用できる型」を見て、今回の内容に合う型のスライドを残して中身を差し替えるのが早い（型ごと作り直すより確実にデザインが揃う）。

### 3. 構造の変更（追加・削除・並べ替え）を先に全部済ませる
- 新しい内容スライドを追加するときは、既存の内容スライド（レイアウトがすでに `title + content placeholder + slide番号` になっているもの、例: slide2.xml）を土台にする:
  ```bash
  node "${CLAUDE_SKILL_DIR}/scripts/duplicate-slide.js" unpacked slide9.xml --after slide9.xml
  ```
  これで新しい `slideN.xml` の作成、`[Content_Types].xml` への Override 追加、`presentation.xml.rels` へのリレーション追加、`presentation.xml` の `<p:sldIdLst>` への挿入まで一括で行われる。**先にこれで枠を全部作ってから、中身のテキスト編集に入る**（複製はファイルコピーなので、編集後に複製すると編集済みの中身までコピーされてしまう）。
  - `duplicate-slide.js --after` は毎回ソースの直後に差し込むので、複数枚まとめて複製すると **順序が逆になる**。枚数を確保したら `<p:sldIdLst>` を丸ごと書き直して並べ替えるのが早い。
- スライドを消す/並べ替える場合は `ppt/presentation.xml` の `<p:sldIdLst>` を直接編集する（該当 `<p:sldId>` を消す/移動する）。
  - **不要になったスライドは `<p:sldIdLst>` から消すだけで終わらせず、`presentation.xml.rels` のリレーション・`[Content_Types].xml` の Override・`ppt/slides/slideN.xml` 実体もまとめて削除する**。表示上は問題ないが、リレーションが残っていると後で python-pptx で保存したときに **ZIP エントリが重複してファイルが壊れる**（python-pptx はリレーション経由でパーツを辿るため）。
- 画像を貼るスライドは、既存の画像入りスライドを複製すると画像パーツへの参照ごとコピーできて楽（同じ画像を指すことになるので、違う画像にしたい場合は新しい画像を `ppt/media/` に追加して該当スライドの `.rels` を書き換える）。

### 4. 各スライドの中身を編集する

**生 XML 編集と python-pptx の使い分け**（混ぜて使うのが一番速い）:

| やること | 手段 |
|---|---|
| テキストの差し替え・微修正、文字サイズ、行間、既存図形の座標 | 生XML（`Read` → `Edit`） |
| チップ／パネル／タイル／帯／チェックリスト／表／模式図の **新規作成**、配色の一括置換 | python-pptx（`deck_style.py` を import） |
| 数式 | 生XML（`omml.js` / `insert_math.js`） |

**順序が重要**: python-pptx で開いて保存すると XML は再シリアライズされるので、**python-pptx の処理を先に全部済ませ、生 XML の手編集は最後**にする（`python-pptx で編集 → 保存 → unzip → 生XML編集 → re-zip`）。逆にすると手編集が壊れることがある。

python-pptx 側の書き方:
```python
import sys; sys.path.insert(0, r"${CLAUDE_SKILL_DIR}/scripts")
from pptx import Presentation
from deck_style import *          # パレット・チップ・パネル等

prs = Presentation(path)
s = prs.slides[6]                 # 0始まり
remove_placeholder(s)             # 既定の本文プレースホルダを外してから面を作る
add_issue_response(s,
    [[("実験結果をもっと分かりやすく示してほしい", False, None)]],
    [[("① ", True, None), ("結果の可視化（図）を追加", False, None)],
     [("② ", True, None), ("新指標", True, None), ("を結果表に追加", False, None)]])   # 太字に色は付けない
print(normalize_bold_color(prs, skip=(2, 3)))   # 据え置きの研究背景(0始まり2,3)は触らない
prs.save(path)
```

**内容スライドを大量に作り替える回のおすすめの組み方**（全27枚の資料もこの方法で作れた）:
1. ベースを展開し、構造変更（削除・`duplicate-slide.js` で枠の確保・`<p:sldIdLst>` の並べ替え）だけ済ませて `stage1.pptx` に固める。枠には、タイトル＋スライド番号だけ残る単純な内容スライドを複製して使う（画像やノートを持つスライドを複製すると不要なリレーションまで増える）。
2. 中身は全部 **1本の python スクリプト（build.py）** に書く: 枠の図形をタイトル・スライド番号以外すべて消す → `add_claim` / `add_panel` / `add_table` / `add_picture` … で組む → `normalize_bold_color` → `stage2.pptx` に保存。
3. unzip → `insert_math.js` → `check-min-font.js` → zip → `check_deck.py` → レンダリング、をシェルスクリプト1本（rebuild.sh）にまとめる。
4. 直しは build.py を編集して rebuild.sh を流し直すだけ。生 XML を手で直さないので、何度でも作り直せる。
   - **`stage1.pptx` と build.py は最後まで消さない**（途中で消すと、追加の修正のたびに構造変更からやり直しになる）。
   - レンダリング結果は PIL で数枚ずつ1枚の画像にまとめてから見ると、確認が速い。

生 XML 側の書き方:
- `Read` で `unpacked/ppt/slides/slideN.xml` を確認してから `Edit` で `<a:t>` の中身を書き換える。
- 箇条書きは1項目=1つの `<a:p>` にする（改行を `<a:t>` の中に入れない）。既存の `<a:pPr>` はそのままコピーして体裁（インデント・スペース）を保つ。
- 太字にしたい語句だけ別の `<a:r>` に分けて `<a:rPr b="1" .../>` を付ける。
- 文字サイズを指定する `sz="NNNN"`（単位はポイント×100。例: 18pt→`sz="1800"`）は **1600未満を書かない**。
- 前後にスペースがある `<a:t>` には `xml:space="preserve"` を付ける。**「・」や空白を消すときに隣接ランの区切りスペースまで消さないこと**（`…の式 ` の末尾スペースを落とすと `式r_p(t+1)` のようにくっつく）。
- タイトルスライド（slide1.xml）は月の数字だけ差し替える。氏名・所属はプロフィールに合わせる（学年が上がって学部→大学院になったら「〇〇学部 〇〇学科／B4」→「〇〇研究科 〇〇専攻／M1」のように更新し、プロフィールも直すか聞く）。
- **本文プレースホルダは自動で「•」が付く**。そこにさらに「・」を書くと `• ・…` と二重になる。プレースホルダを使うなら「・」は書かない（自前のテキストボックス／パネルなら「・」を書いてよい）。
- `Edit` ツールで長い XML 断片を `old_string` にすると一致しないことがある。**短くユニークな断片**（`<a:t>差し替えたい文字列</a:t>` 単位）で置換する。

```bash
node "${CLAUDE_SKILL_DIR}/scripts/check-min-font.js" unpacked 16
```

違反が出たら該当スライドを開いて直す（サイズを上げる／文言を削る／箱を広げる）。ゼロになるまで直す。

### 6. 再ZIPして機械チェック
```bash
cd unpacked && rm -f "../<新しいファイル名>.pptx" && zip -Xr "../<新しいファイル名>.pptx" . && cd ..
```
`zip -Xr` は展開したディレクトリの **中から** 実行すること（外から `zip dir/*` すると余計なパス階層が入って壊れる）。作った直後に `unzip -t "<新しいファイル名>.pptx"` で ZIP 自体が壊れていないか確認する。

続けて機械チェックを流す（`--base` はベースにした pptx、`--skip` は据え置きにして中身を触らないスライドの番号。1始まり）:
```bash
python "${CLAUDE_SKILL_DIR}/scripts/check_deck.py" "<新しいファイル名>.pptx" --base "<ベースファイルのパス>" --skip 3,4 > check_deck.txt
```
出力をファイルに落としてから `Read` で読む（Windows のコンソールに直接出すと日本語が化けることがある）。
- **最後の行が `DONE: …` でなければ検査が途中で落ちている**。0件と見なさず、エラーを読んで直してから流し直す
- **FAIL は必ず 0 にする**（PowerPoint で開けない・修復ダイアログが出る壊れ、16pt 未満）
- **WARN は原則直す**。見積もりなので誤検出もある。直さないものは、レンダリング画像で問題ないと確かめたうえで理由を最後の報告に書く
  - `orphan`（最終行が1〜4字）・`overflow`（はみ出し）: 文を削る／`<a:br/>` で区切る／箱を広げる。**文字を小さくして収めない**
  - `fill`（下の空白）: レイアウトの型で面を作る。**中身を水増ししない・パネルの高さだけ引き伸ばさない**
  - `color` / `bold-color`: パレットの色に戻す／`normalize_bold_color()`。写真の識別ラベルは例外なので残してよい
  - `leftover`: 仮の文字（〇〇・TODO）や同梱テンプレートのダミー文の消し忘れ
  - `wording` / `title`: 上の「文章のルール」に沿って直す。研究上正しい言い方なら残してよい
- 直したら手順6をやり直す（build.py 方式なら rebuild.sh に組み込んでおく）

### 7. 内容チェック
```bash
PYTHONIOENCODING=utf-8 python -m markitdown "<新しいファイル名>.pptx" > check.md
```
で全スライドのテキストを読み、プレースホルダの消し忘れ（「〇〇について」のような仮タイトルの残り、コピー元の回の情報、**同梱テンプレートのダミー文**の消し忘れ）が無いか確認する。**`PYTHONIOENCODING=utf-8` を付けて、出力はファイルにリダイレクトしてから `Read` で読む**こと。Windows で素のままコンソールに出す・`grep` に流すと、日本語が cp932 で化けて読めない。

### 8. 構造チェック（任意）
```bash
# Anthropic 公式 pptx スキルの validate.py を探す（場所は端末ごとに違う。見つからなければこの手順は飛ばしてよい）
VALIDATE=$(find ~/.claude "$APPDATA/Claude" "$HOME/Library/Application Support/Claude" -path "*skills/pptx/scripts/office/validate.py" 2>/dev/null | head -1)
[ -n "$VALIDATE" ] && python "$VALIDATE" "<新しいファイル名>.pptx" --original "<ベースファイルのパス>"
```
テンプレート由来の XSD エラーは `--original` を付ければベースと差分比較され無視される。**Windows では公式 pptx スキルの `scripts/thumbnail.py` は使わない**（内部で Linux 用の `AF_UNIX` ソケットに依存していて `AttributeError` になる）。レイアウト選びは代わりに次のステップの画像で行う。

### 9. 画像で目視確認する

```bash
python "${CLAUDE_SKILL_DIR}/scripts/render_with_powerpoint.py" "<新しいファイル名>.pptx" render_check
```
PowerPoint COM で PDF 化してから PNG にするので **本番と同じ見え方** が確認できる（Windows＋PowerPoint のみ）。`--pages 7,10,13` で特定ページだけ、`--dpi 110` で解像度を指定できる。

PowerPoint が無い環境や作業中の素早い確認は LibreOffice 版（`render_slides.py`、出力は `.jpg`）を使う。ただし **次のものは LibreOffice では正しく見えない**:
- OMML 数式（LibreOffice は Fallback のプレーンテキストを表示する）
- ページ番号（同梱テンプレートは `firstSlideNum="0"` なので、LibreOffice とは1ずれる）

画像を見て次を確認する:
- 文字がボックスからはみ出していないか、**1〜2文字だけ次行に落ちていないか**（18pt で全幅なら約30文字が限界）
- **下半分が空白のまま残っていないか**（残っていたらレイアウトの型で埋める）
- 図・注釈ラベルが重なっていないか、矢印が正しい位置を指しているか
- パネルを重ねたスライドで、後から足した図形と既存ラベルが衝突していないか（**塗りのあるパネルは透明なプレースホルダと違い、重なりがそのまま見える**）
- `check_deck.py` の WARN が出たスライドで、実際に崩れているか（直さずに残す WARN はここで確かめる）

**見た結果は作業フォルダの `qa.md` にスライドごとに1行で書く**。問題が無かったスライドも「該当なし」と書き、飛ばさない（全ページを見たことを自分で確かめるため）。
```markdown
- p.6: 「る指摘」が2行目に1行だけ落ちている → 文言を削った
- p.7: 該当なし
```
最後の報告で「確認した」と書くときは、実際に見たスライド番号を書く。

問題があれば直して手順6〜9をやり直す。確認が終わったら `render_check` / `unpacked` / `qa.md` / `check_deck.txt` は削除する（成果物ではない。ユーザーが残したいと言えば残す）。

### 10. レビューエージェントに添削させる（ユーザーが望めば）

作り手とは別の目で読ませて直す。効果が大きいので、ユーザーに提案してよい。読み手は2種類で、**並行に起動**してよい（どちらも general-purpose のサブエージェント、読み取り専用）。指示文の全文と採否表の書式は [references/review-prompt.md](references/review-prompt.md) にある。
- **A. 教授役**（プロフィールの研究分野が専門で、ゼミ発表を厳しく添削する教員）: 画像・markitdown のテキスト・構成案の md を渡す。論理の流れ、言い過ぎ、構成案との数値の照合、用語の一貫性、図表の読みやすさを見る
- **B. 初見の聞き手**: 画像とテキスト**だけ**を渡し、構成案・このスキル・デザインルールは見せない。最初に自由記述で「質問したくなる点」を挙げさせ、タイトルだけで流れが追えるか、タイトルと図の結論の食い違いなどを見る。「欠点を最低3つ」と指示する

反映の仕方:
- ユーザーの決定（「このスライドはそのまま」「この図を追加」など）や構成案と矛盾する指摘は採用しない。事実の誤り（図と本文の不一致など）と言い過ぎは直す。数値の疑義・意味が変わる言い換えは直さずにユーザーへ報告する
- 両方の指摘を**採否表**（# / 出所 / スライド / 指摘 / 採用・不採用・保留 / 対応・理由）にまとめ、最後にユーザーへ渡す
- 直したら手順6（機械チェック）と手順9（目視）をもう一度通す

ユーザーには最後に一度、実際に PowerPoint で開いて確認してもらうよう伝える。

**Box / OneDrive 同期フォルダの注意**: 同期フォルダ上の pptx を PowerPoint COM で直接開くと `E_FAIL` になることがある。`render_with_powerpoint.py` は自動でローカル一時フォルダへコピーしてから開くので気にしなくてよいが、自分で COM を書くときは同じ対処が要る。

## つまずきやすい点

- スライド番号プレースホルダ（`type="sldNum"`）は自動フィールドなので数字を書き換える必要はない。`<a:t>` に残っているコピー元の数字が markitdown の出力では全部同じに見えるが、PowerPoint が開くときに振り直すので問題ない。
  - 同梱テンプレートは `firstSlideNum="0"`（タイトルを0とカウント）なので、**PowerPoint 上の表示番号は通し枚数より1小さい**。元からの仕様なので勝手に変えない。
- 過去資料で12ptになっている引用文献などを今回さわる場合は、16pt化に伴って箱がはみ出さないか要確認（著者名を省略する、二段になっている引用を一段にする、など）。
- スライドサイズ・フォントは毎回変えない。配色もパレットの2色から出ない。装飾を増やすのではなく、**情報を面（パネル・タイル・帯）に整理する**方向で見やすくする。
- 大きな `.pptx` を作業前に上書きしないよう、必ず新しいファイル名にコピーしてから展開・編集する。
- 文章量は削る方向で。1パネルに3行以上の長文が入ったら、**図で説明できないか**を先に考える（模式図があるスライドは本文を1〜2行に圧縮してよい）。
- よく受ける指摘は順に「**下の余白が大きい**」「**文章が多い**」「**色がちぐはぐ**」「**太字に色を付けて見づらい**」。作り終えたら必ずこの4点で自己点検してから渡す。`check_deck.py` の `fill` / `orphan`・`overflow` / `color` / `bold-color` がそれぞれに対応する（ただし「文章が多い」は機械では測りきれないので、画像でも見る）。
- **python-pptx は保存のときにスライドのファイル名を表示順に振り直す**（`slide10.xml` ＝ 10枚目になる）。構造変更の段階で付けた `slide29.xml` などの番号は、python-pptx で保存したあとは使えない。
- **タイトルスライドのタイトルプレースホルダは下揃え**なので、題目を2〜3行に増やすと下の所属・氏名と重なる。行を増やすときはプレースホルダの `top` を上げる（例: top=750,000、height=2,750,000）。
- 既存スライドのテキストボックスの文言を長くすると、幅が足りずに2行に割れる。文言を短くするか箱を広げるかを、レンダリングで確かめて決める。
- node のテンプレート文字列（`` `…` ``）の中で正規表現を `new RegExp(`…\d…`)` と書くと `\d` が `d` になってマッチしない。正規表現リテラル（`/…\d…/`）を使う。
